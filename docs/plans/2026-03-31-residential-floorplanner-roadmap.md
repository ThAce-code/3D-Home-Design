# 住宅平面设计器长期路线图

> 更新日期：2026-03-31
> 适用仓库：`D:\3D-Home-Design`
> 产品目标：做成像 Pascal 一样方便好用的住宅平面设计器，而不是只停留在墙体原型编辑器
> 文档位置：根目录 `D:\3D-Home-Design\docs\plans`
> 实际开发位置：建筑核心大版本工作应在 `D:\3D-Home-Design\.worktrees\` 下的新独立 worktree 中进行

---

## 1. 背景判断

基于当前项目进度，建筑编辑能力已经完成了从旧 `Room` 模型向 `Level / Vertex / Wall / Zone` 核心的切换，并且 `WallTool V2` 已基本打通以下主链路：

- 画墙草稿与连续提交
- 端点、闭合、正交、墙身吸附
- 墙图修复与 `Zone` 自动重建
- 角点、T 字口、十字口的基础 mesh 补偿
- 墙、地面、zone 的基本命中与选择

这说明项目已经跨过“能不能做建筑编辑”的阶段，进入“如何把它做成长期可维护、可扩展、可产品化的住宅平面设计器”的阶段。

现阶段最大的风险，不是缺几个功能，而是底层边界还不够稳：

- `tool input`、`topology rebuild`、`mesh rendering`、`zone solving` 仍然耦合较紧
- junction、opening、room semantics 还没有标准扩展位
- 选择、吸附、编辑反馈还没有形成统一的交互框架

因此后续路线不建议继续按“发现一个问题修一个 case”的方式推进，而应转成阶段化建设。

## 2. 对 Pascal 的参考结论

Pascal 值得借鉴的重点，不是单个算法，而是产品层和架构层的取舍。

### 2.1 应该借鉴的部分

- 编辑器以浏览器内直接操作为主，低学习成本但反馈明确
- `tool / system / geometry / presentation` 分层清晰
- 先把墙、门窗、房间、家具这些住宅设计核心对象做顺，再做更重的产品能力
- 用户操作以“画、拖、吸附、修改、查看结果”为主，不强迫用户理解底层拓扑

### 2.2 不应该盲目照搬的部分

- 不要为了追求复杂拼角而过早引入过重的几何系统
- 不要在当前内核仍不稳定时直接上多楼层、协作、复杂布尔
- 不要为了外观一致去复制 Pascal 的全部对象模型和渲染方案

本项目更合理的路线是：吸收 Pascal 的分层思想和交互目标，但坚持自主的 TypeScript/React/R3F 实现边界。

### 2.3 参考链接

- Pascal 产品站：<https://pascaleditor.org/>
- Pascal 在线编辑器：<https://editor.pascal.app/>
- Pascal 开源仓库：<https://github.com/pascalorg/editor>

## 3. 总体路线

建议后续版本按下面的主线推进：

`V3 做内核`

`V4 做编辑体验`

`V5 做住宅语义`

`V6 做展示与交付`

`V7+ 做产品化能力`

这条路线的核心逻辑是：

- 先解决“系统是否稳定可扩展”
- 再解决“用户编辑是否顺手高效”
- 再解决“住宅对象是否完整可表达”
- 最后才做“分享、导出、协作、平台化”

## 3.1 实施位置约定

后续建筑核心版本的设计和路线图文档统一保存在根目录 `docs/plans/`。

但实际代码实施不应直接在根目录工作区进行，而应在 `D:\3D-Home-Design\.worktrees\` 下新建独立 worktree 后再开展。

例如：

- 文档：`D:\3D-Home-Design\docs\plans`
- V3 建议工作目录：`D:\3D-Home-Design\.worktrees\architecture-core-v3`

## 4. V3：Architecture Core 2.0

### 4.1 目标

把当前 V2 的“可用墙体编辑”固化为稳定建筑编辑内核，并同步完成一次面向产品化入口和编辑氛围的视觉重置，为后续门窗、房间、楼板、尺寸编辑提供标准基础。

### 4.2 核心成果

- 抽出明确的 `WallToolController`
- 抽出统一的 `SnapEngine`
- 抽出稳定的 `TopologyEngine`
- 抽出可扩展的 `WallMeshBuilder`
- 抽出独立的 `ZoneSolver`
- 统一命中测试、选择优先级、编辑反馈来源
- 新增独立落地页，编辑器改为二级入口
- 设计场景从当前黑色基调切换为浅色、米白、建筑感更强的视觉体系

### 4.3 本阶段必须完成

- 稳定 `wall / vertex / zone` identity
- 从“全量重建导向”逐步转向“增量修复 + 派生重算”
- 定义 junction 类型和连接规则
- 为后续 `opening` 预留墙体局部切割接口
- 为后续 `room semantics` 预留 zone 元数据挂载点
- 补齐拓扑、几何、交互三层回归测试
- 在同一前端中引入路由：`/` 为落地页，`/editor` 为编辑器
- 首页视觉参考 `D:\3D-Home-Design\3d-home-designed`
- 编辑器场景视觉参考 Pascal 的浅色、米白、干净建筑感

### 4.4 本阶段不做

- 门窗
- 家具
- 多楼层 UI
- 完整 CAD 级拼角
- 打印导出
- 云端协作

### 4.5 风险

- 如果继续混用 scene 事件和 tool 状态，V4 会难以推进
- 如果 zone identity 不稳，V5 的房间属性会频繁丢失
- 如果 junction 规则继续靠局部修补，opening 很容易再次破坏 mesh 和 zone

### 4.6 验收标准

- 墙体新增、删除、连接、闭合在同一套工具状态机下运行
- T 字、十字、套圈、桥接等典型平面关系稳定成图
- zone 在重复编辑后 identity 尽量稳定
- 墙和 zone 的命中、选择、删除、撤销行为一致
- 新增一类连接规则时，不需要回头改一圈 UI 逻辑

## 5. V4：Professional Editing UX

### 5.1 目标

把系统从“能编辑”提升到“像真正住宅平面设计器一样顺手”。

### 5.2 核心成果

- 连续画墙、自动续画
- 长度/角度数值输入
- 拖拽顶点、拖拽墙身、墙体偏移
- 分割墙、并墙、延伸墙、修剪墙
- 明显的吸附反馈、对齐提示、尺寸标注
- 更好的撤销/重做颗粒度

### 5.3 本阶段必须完成

- 工具状态机从 `WallTool` 扩展到 `Select / Move / Split / Offset`
- 统一编辑手柄系统
- 屏幕空间尺寸标注和编辑反馈
- 约束系统从“画墙时可用”扩展到“修改时也可用”
- 让常见平面改动不依赖删除重画

### 5.4 本阶段不做

- 完整门窗族库
- 家具方案设计
- 多用户协作

### 5.5 风险

- 如果 V3 没把工具层抽稳，V4 会出现状态冲突和撤销错乱
- 如果尺寸和约束只做显示不进入统一编辑管线，会形成第二套隐式逻辑

### 5.6 验收标准

- 用户可以只靠鼠标和少量快捷键快速搭完整户型
- 用户可以拖改已有户型，而不是频繁删墙重画
- 吸附和约束有明显“吸住了”的感知
- 常见编辑动作在 2D/3D 视图下行为一致

## 6. V5：Residential Semantics

### 6.1 目标

把当前几何编辑器升级为真正的住宅平面设计器。

### 6.2 核心成果

- 门、窗、洞口作为正式对象进入模型
- `Zone` 升级为真正的房间语义对象
- 房间名称、用途、面积、周长、净空信息可编辑
- 墙体支持内外侧语义与基础构造属性
- 引入楼板、天花、基础空间构件

### 6.3 本阶段必须完成

- `Opening` 数据模型和墙体切割规则
- 门窗插入、移动、删除、跟随墙体更新
- 房间属性面板和自动统计
- 房间合并/拆分后的 identity 与属性迁移策略
- 基础住宅构件库：入户门、室内门、窗、推拉门等

### 6.4 本阶段不做

- 复杂幕墙、异形洞口、专业 BIM 属性全集
- 施工图级节点表达

### 6.5 风险

- 如果 opening 只是视觉对象而不进入拓扑，会很快失控
- 如果 zone identity 迁移策略不清楚，房间属性会在编辑后失真

### 6.6 验收标准

- 用户能完成一套住宅平面从墙体到门窗到房间语义的表达
- 房间面积、名称、用途和边界变化保持一致
- 门窗跟随墙体编辑稳定更新，不轻易飘移或失联

## 7. V6：Presentation And Delivery

### 7.1 目标

让设计结果可展示、可复用、可交付。

### 7.2 核心成果

- 2D/3D 联动查看
- 常用家具与设备摆放
- 主题材质与空间氛围预览
- 截图、导出、打印、分享链接
- 模板户型与样板方案

### 7.3 本阶段必须完成

- 家具对象与房间/墙体的基础吸附关系
- 2D 平面和 3D 展示的切换与同步
- PNG/PDF/分享链接等基本输出能力
- 模板项目和快速开始流程

### 7.4 本阶段不做

- 高精度施工图 CAD 导出
- 重资产渲染管线

### 7.5 风险

- 如果前面没有把语义对象建好，V6 会沦为单纯“摆模型”
- 如果 2D/3D 使用两套派生逻辑，展示和编辑很容易不一致

### 7.6 验收标准

- 用户可以从空白项目快速做出可讲解的住宅方案
- 用户可以切换 2D/3D 查看并输出结果
- 家具、门窗、房间信息形成统一展示结果

## 8. V7+：Productization

### 8.1 目标

把编辑器升级为完整产品，而不是本地单机工具。

### 8.2 可能方向

- 项目管理
- 云端保存
- 多端同步
- 协作评论
- AI 户型草案和自动布置
- 多楼层住宅支持
- 导入导出生态

### 8.3 启动前提

- V3 到 V6 的核心链路已经稳定
- 数据模型已经能支撑长期演进
- 输出、分享、对象语义已经形成产品闭环

## 9. 版本之间的依赖关系

- 没有 V3，就不要正式开做 V5
- V4 必须建立在 V3 的稳定内核上
- V5 必须建立在 `stable wall graph + stable zone identity` 上
- V6 必须建立在 `room / opening / furniture` 统一语义上
- V7+ 只在前面几版已形成明确产品价值后再进入

## 10. 当前建议的实施顺序

### 第一优先级

先启动 V3，并把目标收敛为“Architecture Core 2.0”。

### 第二优先级

V3 完成后，优先进入 V4 的编辑体验建设，而不是马上扩功能。

### 第三优先级

只有当 V3 和 V4 都稳定后，才正式启动 V5 的门窗和房间语义。

## 11. 当前的决策结论

从现在开始，项目应以“住宅平面设计器”作为主方向，而不是“3D 场景里附带一个画墙工具”。

因此后续规划应遵循：

- 先做稳定建筑内核
- 再做专业编辑体验
- 再做住宅对象语义
- 最后做展示、交付和平台化

这是最接近 Pascal 产品体验、同时也最适合当前项目阶段的推进路径。
